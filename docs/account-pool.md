# Пул подозрительных аккаунтов

## Что реализовано

1. Сбор кандидатов из владельцев форков репозиториев, активных в трекере
   (растущие, популярные, проверявшиеся пользователями). Список форков обходится
   страницами с сохранением курсора в БД; выбирается давно не посещавшийся
   репозиторий. Среди одинаково давно посещённых приоритет у растущих.
   Поиска пользователей с пустыми профилями и перебора числовых ID нет.
2. Проверка профиля через GraphQL по постоянному node ID. Хранение top-N
   подозрительных аккаунтов, повторная оценка, исключение потерявших признаки
   и недоступных аккаунтов, ограниченный cooldown для отвергнутых кандидатов.
3. Локальный поиск совпадений при построении отчёта, дополнительная проверка
   `suspect_accounts`, повышение нижней границы score и отдельный ряд точек
   `stars_timeline.points[].suspect_accounts` в расширении.

GitHub-отчёты используют node ID репозитория, поэтому переименование не мешает
совпадению, а повторное использование имени другим репозиторием не создаёт
ложного совпадения. В старом режиме GH Archive node ID в снимке отсутствует:
там используется имя без учёта регистра, с ограничением при переименованиях.
Демо-отчёты с mock-проверками не обращаются к реальному пулу.

## Возможности GitHub

[Поиск пользователей](https://docs.github.com/en/search-github/searching-on-github/searching-users)
поддерживает `repos:`, `followers:`, `created:`, но не фильтр по количеству
выставленных звёзд и не предикат «нет активности». Поэтому не используется
широкий поиск пустых профилей: он даёт много обычных пользователей.

[GraphQL User](https://docs.github.com/en/graphql/reference/users) позволяет
получать профиль и `starredRepositories`; у связи со звёздным репозиторием
доступно время `starredAt`. API списка звёзд пользователя также описан в
[REST starring](https://docs.github.com/en/rest/activity/starring).
Сборщик не вызывает ограниченный список stargazers чужого репозитория.

## Правила попадания в пул

По умолчанию одновременно требуются:

- не менее 1000 выставленных звёзд;
- не больше одного собственного публичного репозитория без форков;
- не больше пяти подписчиков;
- не больше двух contributions за последний год: коммиты, issues, PR,
  reviews и доступный агрегат restricted contributions;
- среди последних 100 доступных публичных звёзд минимум две разные минуты
  с 10 и более звёздами; в такие минуты должно попасть не менее 50% выборки.

Оценка для ранжирования: `burstShare × min(1, totalStars / (5 × minStars))`.
Пустой профиль или много звёзд сами по себе не являются достаточным условием.
Отсутствие видимой активности не доказывает отсутствия приватной работы.
Эти правила — начальные эвристики, а не подтверждение злоупотребления.
Логины, ID и список отдельных пользователей в публичный отчёт не передаются.

## Обновление и лимиты

Настройки находятся в `app.account-pool.*` в `application.yaml`.
Сборщик выключен по умолчанию; для включения нужны `ACCOUNT_POOL_ENABLED=true`,
`app.tracker.enabled=true`, PostgreSQL трекера и `GITHUB_TOKEN`.
Схема создаётся механизмом инициализации трекера при старте.

По умолчанию каждые 10 минут и при готовности приложения:

- перепроверяются до 100 аккаунтов, проверявшихся более суток назад;
- очищаются устаревшие записи и лишние отвергнутые кандидаты;
- читается одна страница из 20 форков одного активного репозитория;
- проверяются ещё не проверявшиеся за последние сутки владельцы форков.

Пул содержит максимум 10 000 подозрительных аккаунтов. Cooldown хранит отдельно
до 10 000 непрошедших/вытесненных кандидатов после очистки; они не входят в пул,
их звёзды удаляются. Между очистками число cooldown-записей может кратковременно
превысить лимит на размер прохода. При успешной перепроверке последние 100 звёзд
заменяются транзакционно: снятые звёзды и вытесненные из выборки старые связи
перестают учитываться. Постоянной полной истории звёзд аккаунта нет.

Профили старше трёх суток не участвуют в отчёте даже при сбое очистки.
Ошибки HTTP/GraphQL не превращаются в «чистый профиль» и не стирают предыдущую
выборку. Для сбойного участника пула следующая попытка откладывается на сутки,
чтобы он не блокировал весь обход. Явный отсутствующий node исключается из пула;
это не считается доказательством накрутки. Ошибка страницы сбрасывает курсор
этого репозитория и переносит его в конец очереди.

Верхняя граница одного прохода — 121 GraphQL-запрос (100 обновлений + страница
форков + 20 профилей), без учёта retries транспортного слоя. Это не обещание
121 очка: реальную стоимость определяет GitHub. Проверяется `rateLimit`, при
остатке <=1000 обход прекращается до сброса лимита. Лимит разделяется с трекером
и отчётами; резерв не является глобальной блокировкой расходов других компонентов.
Запускать один экземпляр сборщика: локальный synchronized предотвращает наложение
циклов в одной JVM, но распределённого лидерства нет. Top-N защищён транзакцией БД.

Пропускная способность обновлений — до 14 400 профилей в сутки; ошибки, задержки
и лимиты снижают её. Увеличивая `max-accounts`, нужно согласовать `refresh-batch`,
`interval` и сроки свежести. Обнаружение намеренно медленное: 144 страницы форков
в сутки при настройках по умолчанию; это не полный обход всех репозиториев за день.

## Оценка и график

Считаются совпадения с текущим пулом в полуоткрытом окне отчёта `[from, to)`.
При числе совпадений меньше 5 проверка не влияет на score, но точки на графике доступны.
Начиная с 5, нижняя граница равна `round(70 × min(1, matches / 100))`.
Итог — максимум прежнего score и этой границы. Веса остальных проверок
не пересчитываются; `contribution` новой проверки — фактическое увеличение
score, а `weight=0`, поскольку используется отдельное правило усиления.
В `rules_applied` добавляется `suspect_accounts_floor`, только если score вырос.
Значение confidence 0.7 — эвристическая настройка реализации, не вероятность
того, что пользователь является ботом.

Доля от звёзд репозитория не вычисляется: архив содержит выборку, а данные
трекера отражают чистый прирост со снятиями, поэтому эти знаменатели не дают
надёжной доли всех выставленных звёзд. API сообщает `matched_accounts`,
`pool_size`, `partial_coverage=true`, `sample_limit_per_account=100` и `score_floor`.
При пустом пуле или отсутствии совпадений риск не уменьшается. При сбое БД
основной отчёт возвращается с неактивной проверкой `pool_unavailable`.

Красные точки — число звёзд аккаунтов пула в соответствующем интервале.
Они не суммируются с красными столбцами оценки всплесков: пересечение неизвестно.
Это отдельная серия; `suspicious_stars` и `suspicious_by_check` сохраняют прежний
смысл. Используется существующий шаг графика (дневной для GitHub-отчёта,
внутридневной для архивного); нового отдельного внутридневного графика нет.

## Ограничения и проверка

Пул не исчерпывающий: пользователи без форков не попадут в кандидаты, старые
звёзды вне последних 100 не обнаружатся. Подозрительное поведение в выборке
не означает, что каждая звезда аккаунта неорганическая. Нельзя интерпретировать
число совпадений как доказанное число купленных звёзд.

Добавлены тестовые сценарии классификатора, клиента GitHub, сборщика, отчёта
и PostgreSQL-хранилища: пороги, неполные ответы, приватные связи, лимиты,
курсор, сбои, top-N, повторная загрузка, снятие звёзд, свежесть, переименование,
границы окна, отсутствие снижения score и отдельная серия графика.

В рамках этой задачи сборка, эти тесты и приложение не запускались по просьбе
пользователя. Живые запросы к GitHub и визуальная проверка расширения не проводились.
Тесты PostgreSQL рассчитаны на Testcontainers и пропускаются без Docker.
