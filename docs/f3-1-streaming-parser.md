# F3-1. Потоковый парсер GH Archive — отчёт

> Задача [F3-1](task-board.md) из [плана](plan-next-features.md): streaming-парсер,
> только нужные поля, лёгкий проход 1, ранний фильтр по `repo.name`.
> Ветка `feat/f3-1-streaming-parser`.

## Что изменилось

| Было | Стало |
|------|-------|
| `BufferedReader.readLine()` декодирует каждую строку в `String` | `NdjsonLineReader` режет поток на строки байтами, без декодирования; буфер переиспользуется |
| `JsonMapper.readTree` строит дерево всего события, включая `payload` (~70% байтов строки) | `GhArchiveParser` читает токенами (`JsonParser`): берёт `id`, `type`, `created_at`, `repo.id/name`, `actor.id/login/created_at`, остальное пропускает без объектов и строк |
| Проход 1 индекса полностью разбирает каждое событие, чтобы посчитать звёзды | `EventFilter.stars()`: строка бросается сразу после `type`, если это не `WatchEvent` |
| Проход 2 и запрос одного репозитория разбирают события всех репозиториев | `EventFilter.repos(top)` / `repo(x).or(stars())`: строка бросается сразу после `repo.name` |
| `GZIPInputStream` с буфером 512 байт | буфер 64 КБ |
| Длина строки не ограничена | строка длиннее 16 МиБ пропускается и считается битой (максимум в реальных дампах — ~445 КБ) |

Код: `archive/GhArchiveParser`, `EventFilter`, `NdjsonLineReader`, `GhArchiveDumpReader`;
подключено в `HttpGhArchiveBulkReader`, `HttpGhArchiveClient` и оба прохода `RepoIndexBuilder`.
`GhArchiveBulkReader.readHour(hour, filter, sink)` добавлен default-методом, поэтому
существующие реализации и тестовые заглушки не меняются.

> После [F3-2](f3-2-hourly-aggregates.md) индекс читает каждый час одним полным проходом
> (агрегаты всех репозиториев часа), поэтому фильтры проходов 1/2 в нём больше не нужны;
> ранний фильтр по `repo.name` остался у запроса одного репозитория (`HttpGhArchiveClient`).

## Совместимость с прежним парсером

Прежняя реализация через `readTree` сохранена в тестах как эталон
(`LegacyGhArchiveParser`). `GhArchiveParserEquivalenceTest` требует от нового парсера
того же результата на каждой строке — то же событие, тот же пропуск, та же ошибка —
в строковом и байтовом режимах и с шестью фильтрами:

- ~80 пограничных строк: другой порядок полей, числа вместо строк и наоборот, `null`,
  пустые значения, вложенные `repo`/`actor`/`id` внутри `payload`, экранирование и
  Unicode, глубокая вложенность, битый JSON, битый UTF-8;
- все NDJSON-фикстуры проекта;
- **4 реальных часа GH Archive, 13 652 строки** (запускается вручную, см. ниже) — расхождений нет.

Намеренные отличия:

1. **Значение-объект там, где ждём строку** (`"id": {...}`, `"repo": {"name": {...}}`):
   в Jackson 3 `JsonNode.asText()` на объекте бросает `JsonNodeException`, прежний парсер
   её не ловил — исключение роняло весь час (запрос репозитория или сборку индекса).
   Теперь такая строка просто пропускается.
2. **`parse_errors` считает только строки, которые парсер реально разбирал.** Битая строка
   чужого репозитория, отброшенная фильтром до места поломки, ошибкой не считается.
   Строку, битую в начале (до `type`/`repo`), по-прежнему видно в `parse_errors`.
3. **Строки режутся только по `\n`** (завершающий `\r` отбрасывается). Одиночный `\r`
   внутри строки — пробел для JSON; прежний `readLine()` резал по нему строку надвое.
4. **Строка длиннее 16 МиБ** пропускается и учитывается в `parse_errors` — защита heap.

## Бенчмарк

4 реальных часовых дампа (`2026-11-10-12`, `-15`, `-18`, `2026-11-11-3`): 13 652 строки,
12,6 МБ gzip / 62,7 МБ JSON. Apple M4, JDK 25, один поток; медиана из 15 прогонов после
5 разогревочных. Аллокации — `ThreadMXBean.getCurrentThreadAllocatedBytes` за прогон.

| Конвейер | Время, мс | МБ JSON/с | Аллокации, МБ | Ускорение |
|---|---:|---:|---:|---:|
| распаковка gzip без разбора | 107,2 | 585 | 0,1 | — |
| прежний: readLine + readTree | 271,3 | 231 | 493,9 | 1,0× |
| потоковый: полный разбор (без фильтра) | 155,4 | 404 | 41,3 | 1,7× |
| потоковый: проход 1 индекса, только звёзды | 104,5 | 600 | 15,4 | **2,6×** |
| потоковый: проход 2 индекса, 842 репозитория со звёздами | 110,7 | 566 | 18,1 | **2,4×** |
| потоковый: один репозиторий + звёзды для C4 | 109,5 | 573 | 17,6 | **2,5×** |
| прежний без gzip: readLine + readTree | 172,8 | 363 | 493,8 | 1,0× |
| потоковый без gzip: полный разбор | 61,6 | 1019 | 41,1 | 2,8× |
| потоковый без gzip: проход 1, только звёзды | 13,4 | 4696 | 15,1 | **12,9×** |
| потоковый без gzip: проход 2, 842 репозитория | 18,3 | 3432 | 17,9 | **9,5×** |
| потоковый без gzip: один репозиторий + звёзды | 17,2 | 3649 | 17,4 | **10,1×** |

Итог:

- **сам разбор быстрее в 2,8× без фильтра и в 9,5–12,9× в реальных сценариях** —
  цель плана «2–5×» перекрыта;
- **весь конвейер с распаковкой — 2,4–2,6×**: теперь он упирается в gzip
  (проход 1 — 104 мс при 107 мс на «только распаковку»);
- **мусора в 12–32 раза меньше** (494 МБ → 15–41 МБ на 63 МБ JSON) — меньше давления на GC
  при параллельной сборке индекса и в бюджете памяти F3-6.

Проверка на живом сервисе (HTTP-режим, 2026-11-11): индекс топ-1000 собран по реальному
GH Archive через новый ридер — 1000 репозиториев, 6/6 часов, `parseErrors=0`, `StarIndex`
за все 6 часов. Сборка заняла 507 с, но почти всё — скачивание: сеть до data.gharchive.org
в момент проверки отдавала от 60 КБ/с до 1,2 МБ/с, а потоки разбора потратили на CPU
доли секунды.

Важно для F3-2: раз узкое место — распаковка, а индекс читает каждый час дважды
(проход 1 и проход 2), следующий большой выигрыш — разбирать час один раз
(почасовые compact-агрегаты из F3-2), а не ускорять парсер дальше.

## Как воспроизвести

```bash
mkdir -p /tmp/gharchive
for h in 2026-11-10-12 2026-11-10-15 2026-11-10-18 2026-11-11-3; do
  curl -sSf -o /tmp/gharchive/$h.json.gz https://data.gharchive.org/$h.json.gz
done

# сверка с прежним парсером на реальных дампах
./mvnw test -Dtest=GhArchiveParserEquivalenceTest -Dgharchive.dumps=/tmp/gharchive

# бенчмарк; таблица также пишется в target/gharchive-parser-benchmark.md
./mvnw test -Dtest=GhArchiveParserBenchmark -Dgharchive.benchmark=/tmp/gharchive
```

Без флагов оба теста пропускаются, CI в сеть не ходит.

## Наблюдение по данным

Во всех четырёх проверенных часах нет ни одного `PushEvent` (0 из 13 652 событий).
Если так и останется, метрики с пушами (активность в C3, счётчик `pushes` в статистике)
на реальных данных всегда получают 0 — это стоит учесть при калибровке.
