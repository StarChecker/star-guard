# F4-1. Long-tail индекс всех репозиториев окна — отчёт

> Задача [F4-1](task-board.md) из [плана](plan-next-features.md): long-tail индекс всех
> репозиториев окна. Ветка `feat/f4-1-long-tail-index` поверх
> [F3-2](f3-2-hourly-aggregates.md) (PR #14).

## Зависимость от F3-3

По доске F4-1 ждёт F3-3 (tiered-модель). Но после F3-2 почасовые дайджесты уже держат
агрегаты **всех** репозиториев окна, поэтому long-tail отвечает прямо из них. F3-3
меняет только формат хранения (примитивные массивы, long-tail без `ActorActivity`),
а контракт `RepoIndexSnapshot.lookup` остаётся прежним.

## Что изменилось

| Было | Стало |
|------|-------|
| Индекс отвечает только по топ-N, остальным — `404 REPO_NOT_INDEXED` | Вне топа, но с событиями в окне — отчёт из дайджестов часов; 404 — только если событий в окне не было |
| Отчёт не показывает, из какой части индекса он собран | `source.tier`: `top` / `long_tail` (тип `source.type = gh_archive_index` прежний — расширение показывает «индекс GH Archive») |
| `GET /api/v1/index/repos` сообщает только размер топа | плюс `window_repos` — сколько репозиториев окна отдаётся из индекса (топ + long-tail) |
| Бейдж и пакетная проверка зависимостей для репозитория вне топа — `not tracked` | Получают оценку, если у репозитория были события в окне |

Код: `RepoIndexSnapshot.lookup` / `windowRepoCount` и компонент `digests` (те же объекты,
что держит сборщик), `IndexHit`, `DataSource.Tier`, `IndexRepoDataProvider`;
DTO: `SourceDto.tier`, `TopReposResponse.windowRepos`.

Полнота данных long-tail та же, что у топа: счётчики, минутный ряд звёзд, акторы для C2,
индекс звёзд для C4. Разница одна: возраст аккаунтов из GitHub API дозапрашивается только
для топа (по месту в топе), long-tail получает `starRank = null`.

## Цифры

7 реальных часов GH Archive (2026-11-10 12…17 UTC), окно 6 ч, топ-1000, без сети:

| | Значение |
|---|---:|
| Репозиториев с событиями в окне | 15 070 |
| из них отдаются из long-tail (вне топ-1000) | 14 070 |
| Ответ индекса по long-tail (поиск + композиция подокна), p50 | 0,029 мс |
| p95 / p99 | 0,037 / 0,046 мс |
| max | 1,8 мс |
| Дополнительная память | 0 — снимок ссылается на дайджесты сборщика (≈ 6,9 МБ на 6 часов, см. F3-2) |

Цель плана для long-tail — 1–3 с на запрос; ответ индекса укладывается в доли миллисекунды,
остальное время запроса — скоринг и JSON, они такие же, как для топа.

## Проверка

- `IndexedCoreIntegrationTest`: репозиторий вне топ-2 → 200, `source.tier = long_tail`;
  без событий в окне → 404 `REPO_NOT_INDEXED`;
- `IndexRepoDataProviderTest`: long-tail собирается из дайджестов с пустыми часами,
  `starRank = null`; топ по-прежнему с местом;
- `RepoIndexBuilderTest`: `lookup` в снимке, собранном сборщиком, и `windowRepoCount`;
- бенчмарк по флагу: `./mvnw test -Dtest=RepoIndexBuilderBenchmark -Dgharchive.window=/dir`
  (каталог с часами, см. отчёт F3-2), таблица — `target/long-tail-benchmark.md`.
