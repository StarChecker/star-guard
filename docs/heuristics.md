# Как Star Guard оценивает подозрительность звёзд

## Получение данных

Через GitHub API получаем доступную историю числа звёзд и активность репозитория:
коммиты, issues, pull requests и форки. Собственный трекер раз в пять минут
сохраняет число звёзд, позволяя обнаруживать короткие всплески и последующие падения.
GH Archive используется как дополнительный, неполный источник публичных событий.

Для анализа аккаунтов идём в обратную сторону: берём владельцев форков
отслеживаемых репозиториев, проверяем их профили и последние 100 выставленных
звёзд со временем. Подозрительные аккаунты сохраняем в ограниченный, регулярно
обновляемый пул. Список поставивших звезду чужому репозиторию для этого не нужен.

## Почему выбраны эти признаки

Отправная гипотеза: при искусственном продвижении можно массово увеличить число
звёзд, не воспроизводя разнообразное поведение заинтересованной аудитории.
Поэтому проверяем несколько сторон этого поведения. Это обоснование выбора
метрик, а не утверждение, что любые отклонения означают накрутку.

| Признак | Как оцениваем | Почему он полезен и где может ошибаться |
| --- | --- | --- |
| Резкий рост | Сравниваем дневной приток с медианой предыдущих 28 дней; отдельно ищем короткие всплески по снимкам трекера. Учитываем и кратность роста, и абсолютный размер. | Пакетная закупка может создавать скачки. Но релиз или публикация тоже могут дать резкий органический рост. Медиана уменьшает влияние прошлых единичных всплесков на базовую линию. |
| Звёзды без разработки | Сопоставляем коммиты, issues и PR с притоком звёзд; для зрелого проекта при наличии истории вычитаем ожидаемый обычный приток. | Массовые звёзды без сопутствующей активности заслуживают внимания. Однако справочники и законченные библиотеки могут быть популярны без постоянной разработки. |
| Много форков относительно звёзд | Проверяем отношение новых форков к звёздам у молодых проектов, ослабляя сигнал на малых объёмах. | Совместное массовое выставление звёзд и создание форков может быть признаком кампании. Шаблоны и учебные проекты также естественно получают много форков. |
| Необычное распределение по часам | Сравниваем суточное распределение прироста с общей картиной, собранной трекером. | Автоматизация может концентрировать действия в определённые часы. География аудитории тоже влияет на ритм, поэтому это вспомогательный сигнал. |
| Последующие падения | Считаем объём и долю отрицательных изменений числа звёзд. | Это позволяет заметить массовые снятия звёзд, в том числе возможные чистки аккаунтов. Причину падения по одному счётчику установить нельзя. |
| Аккаунты из подозрительного пула | Ищем звёзды проверяемого репозитория среди сохранённых связей аккаунтов пула. | Дополняет агрегатные аномалии наблюдаемым поведением аккаунтов. Пул неполный, а принадлежность к нему не доказывает неорганичность каждой звезды. |

## Как формируется пул аккаунтов

Одной «пустоты» профиля недостаточно. По умолчанию одновременно требуются:

- не менее 1000 выставленных звёзд;
- не больше одного собственного публичного репозитория без форков и пяти подписчиков;
- не больше двух учитываемых contributions за последний год;
- минимум две разные минуты с десятью и более звёздами, причём в такие минуты
  должно попасть не менее половины выборки последних 100 звёзд.

Так мы сочетаем три признака: большой объём, мало видимой деятельности и повторные
плотные серии действий. Это более избирательное условие, чем любой признак отдельно,
но его точность ещё нужно измерить. Приватная работа может быть не видна.
Для ранжирования используем долю звёзд в таких сериях, умноженную на
`min(1, число звёзд / 5000)`. Храним top-N, по умолчанию 10 000 аккаунтов;
данные старше трёх суток исключаются из оценки.

## Итоговая оценка

Основные проверки дают значения от 0 до 1. Движок объединяет проверки
с достаточной уверенностью взвешенным средним и переводит результат в шкалу
0–100. Сочетание нескольких сильных сигналов может повысить нижнюю границу
оценки. Недостающие данные не считаются доказательством нормального поведения.

Сигнал пула учитывается отдельно и может только повысить score. При пяти и более
совпадениях нижняя граница составляет `round(70 × min(1, совпадения / 100))`.
Ноль совпадений не снижает риск: мы видим только часть аккаунтов и их звёзд.
На графике совпадения показаны отдельными точками и не суммируются с оценкой
всплесков, поскольку эти множества могут пересекаться.

## Что можно утверждать о работоспособности

Метрики имеют объяснимую связь с возможными механизмами накрутки, учитывают
обычную историю проекта, объём данных и несколько разных признаков. Пороги
при этом выбраны как начальные инженерные гипотезы, а не получены обучением
на размеченной выборке. Score — индекс подозрительности, не вероятность накрутки.

Для новой логики добавлен 21 тестовый сценарий, но они пока не запускались.
Даже успешные программные тесты подтвердят корректность реализации правил,
а не точность обнаружения накрутки. Чтобы доказать практическую пользу, нужно
проверить систему на независимой размеченной выборке, измерить precision/recall
и ложные срабатывания на органических всплесках, а затем сравнить результат
с отдельными метриками. Пока корректная формулировка: **обоснованный набор
проверяемых эвристик; эффективность на реальных данных ещё не подтверждена**.
