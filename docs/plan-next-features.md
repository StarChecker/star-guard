# Star Guard — план следующих фич (пул задач)

> Статус: черновик на согласование · База: `main` = `2e294e3` (2026-11-10)
> Проверка базы: `mvn clean test` на JDK 25 — **160 тестов, 0 ошибок**.
> Текущая карта фич: [docs/feature-map.md](feature-map.md).

## 0. Что уже есть по вашим четырём пунктам

### 0.1. Статистика в расширении — **частично сделано**

Уже есть:

- API `GET /api/v1/repos/{owner}/{name}` отдаёт `stats` и `stars_timeline`:
  `forks`, `issues`, `pull_requests`, `pushes`, `unique_actors`, `peak_stars_10m`,
  звёзды по часам (`api/dto/StatsDto.java`, `StarTimelineDto.java`);
- в карточке расширения блок «Подробнее» уже показывает `forks / issues / PR`,
  `pushes` и пик звёзд (`extension/src/ui.js`, `evidence()`);
- таймлайн уже делит столбцы на обычные и подозрительные (`bar-ok` / `bar-bad`),
  есть `suspicious_stars` и `suspicious_by_check` (`StarTimelineService`).

Не хватает для вашего сценария:

- **списка подозрительных аккаунтов** (сейчас только агрегаты/хэши, нет login
  и причины по каждому аккаунту);
- **явных интервалов всплеска** (`spike_intervals[]`), чтобы подсветить на графике
  не отдельные столбцы, а весь участок «накрутки»;
- **числа контрибьюторов** (сейчас `unique_actors` включает и звёзды; в индексе
  акторы к тому же суммируются по часам без дедупликации);
- вывода этих данных в верхнюю часть карточки и в preview-фикстуры.

### 0.2. MCP-сервер с нейросетью — **не сделано**

В репозитории нет ни MCP-сервера, ни зависимостей MCP/LLM (проверено по
`pom.xml`, `extension/`, `action/`). REST-сервис для этого уже удобен:
`GET /api/v1/repos/...`, `POST /api/v1/scans`, `GET /api/v1/scans/{id}`,
`POST /api/v1/repos/batch`, `GET /api/v1/index/repos`.

### 0.3. Ускорение парсинга и 100 000 репозиториев — **не сделано**

Сейчас индекс — топ-1000 (`app.index.top-n`). Узкие места:

- **два полных прохода** по часам окна: `RepoIndexBuilder` скачивает и парсит
  каждый часовой дамп дважды;
- **Jackson `readTree` на каждую строку** в `GhArchiveParser`: строится дерево
  всего события, включая `payload`, который не используется; имя репозитория
  извлекается после полного разбора;
- **память на акторов**: `RepoHourAggregate` хранит `List<ActorActivity>`
  (≈230–260 Б на актор-час). Для 100k репозиториев × 6 часов это единицы–десятки ГБ;
- `rank()`/`top()` сортируют весь индекс на каждый запрос, `starsByMinute()`
  клонирует массив при каждом чтении;
- в индексе нет дедупликации `event_id` (в отличие от `StatsAggregator`);
- при обновлении snapshot старый и новый живут одновременно (пик памяти ×2).

### 0.4. Добавление репозитория и статистика за 1–3 с — **частично сделано**

Есть асинхронный скан для репозитория вне индекса:

- `POST /api/v1/scans` → 202 + `id`, `GET /api/v1/scans/{id}` — прогресс/результат;
- дедупликация задач, кэш 30 минут, 2 воркера (`scan/ScanService.java`);
- расширение уже умеет: 404 `REPO_NOT_INDEXED` → кнопка «Проверить» → polling.

Но холодный скан произвольного репозитория **не укладывается в 1–3 с**: он
скачивает и парсит все часовые дампы окна (десятки секунд–минуты, сотни МБ).
Эндпоинта «добавить репозиторий в индекс» нет; в индекс попадают только топ-N
по звёздам.

## 1. Целевые показатели (SLO)

| Метрика | Сейчас | Цель |
|---------|--------|------|
| Репозиториев в индексе | 1 000 | **100 000** (компактные агрегаты), полный actor-detail — для top-10k |
| Ответ по индексированному репозиторию | O(1), но сортировка/клоны | **p95 < 100 мс**, без аллокаций O(N log N) |
| Парсинг дампа | Jackson tree | **2–5× быстрее**, только нужные поля |
| Сборка индекса | 2 прохода, полный rebuild | первый build — 2 прохода; далее **инкрементально по часу** |
| Память индекса | до ~1–2 ГБ при top-1000 и больших акторах | **≤ 2–4 ГБ** при 100k (конфигурируемо) |
| Произвольный репозиторий с событиями в окне | минуты (скан) | **1–3 с** из long-tail индекса |
| Произвольный репозиторий без событий/вне long-tail | минуты (async scan) | 202 + прогресс; опционально <1 с preview из GitHub API |

## 2. Архитектурные решения, которые нужно зафиксировать

| # | Решение | Рекомендация |
|---|---------|--------------|
| A1 | Что значит «1–3 с для произвольного репозитория» | Гарантировать 1–3 с только для репозиториев, у которых есть события в окне (long-tail компактный индекс). Холодный/пустой репозиторий — честный async `202` + прогресс; опционально быстрый GitHub-API preview |
| A2 | Тир индекса | **Top-N (100k)**: счётчики + `starsByMinute` + star actor IDs. **Detail tier (10k)**: полные `ActorActivity` (login/accountCreatedAt/lastActivity). Long-tail (все репозитории окна): счётчики + star actor IDs, без минутного ряда |
| A3 | Парсер | Streaming Jackson `JsonParser`, только нужные поля, early-filter по `type`/`repo.name`; отдельный lightweight путь для pass 1 |
| A4 | Обновление индекса | Первый build — два прохода; далее хранить почасовые агрегаты и на новом часе парсить только новый час, сдвигая окно |
| A5 | MCP | Отдельный сервис `mcp/` на Node/TypeScript (`@modelcontextprotocol/sdk`), core не меняется; LLM — provider-agnostic (Anthropic/OpenAI-compatible) |
| A6 | LLM-роль | LLM **не пересчитывает score**, а интерпретирует детерминированный отчёт; обязательны `mocked`, `insufficient_data`, покрытие архива и дисклеймер |

## 3. Пул задач

Приоритеты: **P0** — блокирует другие задачи; **P1** — основная ценность;
**P2** — можно после MVP. Оценки — человеко-дни, грубо.

### F1. Расширение: статистика, аккаунты и подсветка всплесков

**Цель:** в карточке репозитория видно: подозрительность аккаунтов, участок
предполагаемого всплеска (выделен цветом), форки/issue/пушы/контрибьюторы.

| ID | Задача | Оценка | Зависимости |
|----|--------|--------|-------------|
| F1-1 | API: `spike_intervals[]` в `StarTimelineDto` (from/to, stars, ratio, peak, suspicious=true/false) | 1–2 | — |
| F1-2 | API: `suspicious_actors[]` (login/hash, reasons: fresh/overlap, account_created_at, first_seen, shared_repos) + `contributors` в `StatsDto` | 3 | F3-3 (для индекса), C2/C4 real |
| F1-3 | Extension UI: полоса интервала всплеска на графике, список аккаунтов, плитки форков/issues/пушей/контрибьюторов | 3 | F1-1, F1-2 |
| F1-4 | Preview-фикстуры, JUnit/MockMvc-тесты, OpenAPI, README | 2 | F1-1…F1-3 |

**Детали реализации:**

- `StarTimelineService` уже помечает подозрительные столбцы; добавить вычисление
  интервалов из `starsByMinute` + C1 `details` (`window_start`, `max_burst_10m`,
  `ratio`) и флаг `suspicious` по реальной активной C1.
- Для C2/C4 собрать аккаунты: `ActorActivity.login` уже есть в прямом скане и
  в `RepoHourAggregate.actors`; в индексном пути нужен merge акторов по часам
  и дедупликация по `actorId`. Хэши оставить как fallback/приватный режим.
- Контрибьюторы: distinct non-star actors (fork/push/issues/PR), дедуп между
  часами; в индексе для top-N хранить actor IDs, для long-tail — только count.
- Конфиг: `app.api.expose-actor-logins` (по умолчанию `false` — хэши),
  `app.api.suspicious-actors-limit` (например, 20).
- UI: новые поля в `extension/src/ui.js` (`timeline()`, `evidence()`,
  `reportView()`), `preview/samples.js`; никакого `innerHTML` с данными.
- **DoD:** на `demo/farm-target` видны подсвеченный интервал, аккаунты с причинами
  и счётчики; на `demo/organic-app` — пусто/нейтрально; работают index и scan пути;
  тесты и preview обновлены.

### F2. MCP-сервер + LLM-трактовка

**Цель:** агент/IDE перед подключением open-source библиотеки вызывает MCP-инструмент,
получает score, уровень и структурированную трактовку (suspicious / borderline /
healthy / insufficient), причины и рекомендацию.

| ID | Задача | Оценка | Зависимости |
|----|--------|--------|-------------|
| F2-1 | Каркас `mcp/` на TypeScript + `@modelcontextprotocol/sdk`, конфиг `STAR_GUARD_API_URL`, stdio-транспорт | 2 | — |
| F2-2 | MCP-инструменты: `get_repo_report`, `start_scan`, `get_scan`, `list_indexed_repos`, `batch_summaries`, `get_badge` | 2 | F2-1 |
| F2-3 | LLM-слой: structured output, provider abstraction (Anthropic/OpenAI-compatible), таймауты/ретраи, fallback на `ExplainTexts.verdict` | 2–3 | F2-2 |
| F2-4 | Guardrails: `mocked`/`insufficient_data`/покрытие архива в промпте; нейтральный тон; без PII/секретов; кэш ответов | 1–2 | F2-3 |
| F2-5 | Compose-сервис, Dockerfile, конфиг Claude Desktop/Cursor, интеграционные тесты с fake core + fake LLM | 2 | F2-4 |

**Схема ответа MCP-инструмента `assess_dependency`:**

```json
{
  "repository": "owner/name",
  "score": 72,
  "level": "high",
  "verdict": "Заметные признаки накрутки: главный сигнал — «пересечение аккаунтов».",
  "interpretation": {
    "category": "suspicious",
    "confidence": "medium",
    "reasons": ["30 аккаунтов ставят звёзды 5 репозиториям", "пик 31 звезда за 10 минут"],
    "recommendation": "review_before_use",
    "caveats": ["score частично на mock-проверках", "2 часа архива отсутствуют"]
  },
  "disclaimer": "Это признаки, а не доказательство накрутки."
}
```

**Сценарий для репозитория вне индекса:** `404 REPO_NOT_INDEXED` → MCP запускает
`POST /api/v1/scans`, опрашивает `GET /api/v1/scans/{id}` с таймаутом (например,
60 с); если не успел — возвращает `scan_id` и статус, не блокируя агента.
LLM вызывается только по готовому отчёту. Ключи — только в env MCP-сервиса,
core их не видит.

**DoD:** MCP подключается к Claude Desktop/Code; для indexed-репозитория отдаёт
структуру выше; для вне индекса — запускает скан и корректно возвращает прогресс;
есть тест с fake HTTP/LLM; документация по установке и переменным окружения.

### F3. Ускорение парсинга и масштаб 100k

**Цель:** индекс на 100k репозиториев с ограниченной памятью, быстрый парсинг,
предсказуемое время обновления.

| ID | Задача | Оценка | Зависимости |
|----|--------|--------|-------------|
| F3-1 | Streaming-парсер (`JsonParser`): только `id/type/created_at/repo/actor`; lightweight событие для pass 1; ранний фильтр по репозиторию | 3 | — |
| F3-2 | Кэш/хранение часов: не парсить один и тот же час дважды; почасовые compact-агрегаты; инкрементальный сдвиг окна | 3 | F3-1 |
| F3-3 | Компактные агрегаты: примитивные массивы вместо `List<ActorActivity>` для top-N; long-tail — только counts + star actor IDs; tiering (top-100k / detail-10k) | 4 | F3-2 |
| F3-4 | Быстрый запрос: предвычисленные `totalStars`/rank, read-only `starsByMinute`, лимит `/index/repos` > 5000, дедуп event_id | 2 | F3-3 |
| F3-5 | C4 на 100k: инвертированный `actor→repos` или предвычисленные overlaps; candidate pool; отказ от O(N) скана на запрос | 2 | F3-3 |
| F3-6 | Бенчмарк/профилирование: синтетические 100k, heap, build time, p95 API; JMH/скрипт; memory budget в конфиге | 2 | F3-3 |

**Ключевые изменения:**

- `GhArchiveParser` — новый потоковый метод `parseLight` (pass 1) и `parse`
  (pass 2) без `readTree`; `HttpGhArchiveBulkReader` получает pre-filter.
- `RepoHourAggregate` — заменить `List<ActorActivity>` на `long[] actorIds` +
  `int[] firstSeen`/`int[] lastActivity`/`byte[] flags` или на counts; полный
  `ActorActivity` — только detail-tier.
- `RepoIndexSnapshot` — `Map` репозиториев + отдельный отсортированный
  `topByStars`/`ranks`, чтобы не сортировать на каждый запрос.
- `RepoIndexBuilder` — первый build два прохода; следующие обновления — один
  новый час + сдвиг окна; хранить per-hour aggregates.
- `RepoIndexLifecycle` — атомарная подмена, отказаться от двойного пика памяти
  (стриминг/освобождение старого snapshot).
- Конфиг: `app.index.top-n: 100000`, `detail-tier-size: 10000`,
  `memory-budget-mb`, `max-per-repo-actors`, `parse-threads`.

**DoD:** 100k репозиториев в снапшоте; память в согласованном бюджете; парсер
в 2–5× быстрее на бенчмарке; p95 индексного ответа < 100 мс; существующие
160 тестов + новые зелёные; отчёт с цифрами до/после.

### F4. Добавление репозитория и ответ за 1–3 с

**Цель:** репозиторий, которого нет в top-100k, можно «поднять» в индекс, а по
произвольному репозиторию с событиями в окне получать статистику за 1–3 с.

| ID | Задача | Оценка | Зависимости |
|----|--------|--------|-------------|
| F4-1 | Long-tail компактный индекс всех репозиториев окна (counts + star actor IDs) в том же проходе; лимиты памяти | 4 | F3-3 |
| F4-2 | `POST /api/v1/index/repos` / `PUT /api/v1/index/repos/{owner}/{name}`: добавить/закрепить репозиторий, идемпотентно; 200 с отчётом или 202 со scan id | 2 | F4-1 |
| F4-3 | Приоритетный scan-job: продвижение в очереди, прогресс, кэш, TTL pinned-репозиториев, выживание при rebuild | 2 | F4-2 |
| F4-4 | GitHub API preview для холодного/пустого репозитория (звёзды/форки/issues/контрибьюторы) + async полный score (опционально) | 2 | F4-2 |
| F4-5 | Тесты: warm long-tail ≤3 с, cold → 202, идемпотентность, pinned после пересборки; бенчмарк | 1 | F4-1…F4-4 |

**Важно:** 1–3 с для **холодного** репозитория без событий в окне невозможны
без внешнего OLAP/предварительной загрузки всех дампов. Рекомендуемая честная
семантика:

- есть события в окне → long-tail lookup, **200** за 1–3 с;
- нет событий/нет long-tail → **202** + `scan_id` (существующий UX расширения);
- опционально `GitHub API preview` за <1 с, но это базовая статистика, не
  полный suspicious score.

**DoD:** добавление репозитория идемпотентно; warm-репозиторий отдаётся ≤3 с;
cold возвращает 202/прогресс; pinned-репозиторий переживает пересборку в
пределах TTL; ошибки/лимиты описаны в OpenAPI; тесты и бенчмарк.

## 6. Риски и открытые вопросы

| Риск | Митигация |
|------|-----------|
| 100k × 6h × акторы не влезает в память | Compakt-tier (counts + star IDs), detail только top-10k, memory budget и алерты |
| Два прохода по дампам долго | Кэш/хранение часов, инкрементальный rebuild, параллелизм, профилирование |
| 1–3 с для холодного репо недостижимы | Честный async 202 + long-tail для событий окна; GitHub preview как опция |
| LLM ошибочно трактует mock/insufficient | Guardrails в промпте, передача `mocked`/coverage, fallback на детерминированный verdict |
| MCP-скан зависит от single-instance `ScanService` | Один scan-backend или общий store (Redis/БД) перед масштабированием |
| Приватность actor login | По умолчанию хэши, конфиг `expose-actor-logins`, лимит выборки |
| C1 по умолчанию mock → подсветка «накрутки» неактивна | Для демо включать `app.scoring.checks.burst.mode=real`; иначе показывать «всплеск» нейтрально |

**Вопросы для согласования:**

1. 1–3 с считаем гарантией только для репозиториев с событиями в окне (long-tail)? Или нужен внешний OLAP для любых репозиториев?
2. 100k — это top-100k по звёздам с полными счётчиками, а actor-detail только top-10k — ок?
3. LLM: какой провайдер/модель и допустимо ли отправлять публичные данные репозитория во внешний API? Нужен ли локальный LLM?
4. MCP-транспорт: stdio для Claude Desktop/Code или ещё Streamable HTTP для хостинга?
5. Показывать ли login аккаунтов в расширении или только хэши/причины?
6. Делать ли GitHub-API preview для холодных репозиториев (быстро, но неполный score)?
