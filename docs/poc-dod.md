# Star Guard PoC — Definition of Done по веткам

> Источник: «DevDays Fall 2026. Star Guard.xlsx», лист «Лист1» (план на 10.11,
> критерии к вечеру, ветки). Документ фиксирует DoD PoC так, чтобы по ветке
> и PR можно было однозначно понять, какая часть проекта выполнена.
>
> Статус в §4 актуален на **2026-11-10** и обновляется при мерже веток
> в `feature/core`.

---

## 1. Правила ветвления и приёмки

| Правило | Как проверяем |
|---------|---------------|
| Ветка создаётся от `feature/core` | `git merge-base` ветки и `feature/core` = голова `feature/core` на момент создания |
| Ветка мержится обратно в `feature/core`, не в `main` | в PR base = `feature/core` |
| Один PR = одна проверка (C1…C5) или одна задача | в PR изменены только файлы этой проверки, конфиг, фикстуры и тесты |
| Одно ревью на PR, CI зелёный | review approved + workflow `CI` успешен |
| Размер правки — вертикальный срез | новая проверка + пороги + фикстуры + тесты + README в одном PR |

**Маркеры статуса:** ✅ готово и в `feature/core` · 🟡 PR открыт/на ревью ·
🔵 в работе (ветка есть, PR нет) · ⬜ не начато.

## 2. Общий DoD PoC (для любой ветки)

PR не мержится в `feature/core`, пока не выполнено всё:

- [ ] `mvn test` (или `mvn -B verify`) зелёный на **JDK 25**, офлайн, без доступа к GH Archive;
- [ ] пороги и веса проверки лежат в `application.yaml`, магических чисел в коде нет;
- [ ] проверка видна в ответе API: `score.checks[]` содержит её `id`, `score`,
      `confidence`, `weight`, `contribution`, `active` и `details` (explain);
- [ ] демо «плохая/здоровая» фикстура: реальная проверка даёт ожидаемый скор
      (накрутка — высокий, здоровая — низкий), оба сценария воспроизводятся curl-запросом;
- [ ] `README.md` и `docs/openapi.yaml` соответствуют поведению (флаги, формулы, примеры);
- [ ] в PR одно ревью, замечания закрыты, CI зелёный.

### 2.1. Шаблон DoD для реальной проверки Cx

Единый формат, по которому принимаются C1–C5 (выведен из DoD C3):

- [ ] бин реализует `RepoCheck`, `id()` из `CheckIds`, возвращает `CheckResult` с `score`/`confidence` в `[0, 1]`;
- [ ] при недостатке данных `confidence < min-confidence` — движок сам исключает проверку из score;
- [ ] переключатель `mock | real`: `app.scoring.checks.<id>.mode` (по умолчанию
      `${app.scoring.mode:mock}`), ровно один бин на `id` в контексте;
- [ ] типизированный `@ConfigurationProperties` с валидацией порогов; опечатка
      в режиме роняет старт, а не отключает проверку молча;
- [ ] `details` в explain: `mocked=false`, входные значения и пороги
      (по ним можно вручную пересчитать score);
- [ ] unit-тесты: формула, границы (порог, gate, деление на ноль), пороги из конфига,
      невалидный конфиг;
- [ ] интеграционный тест через REST на фикстурах (плохая ≥ ожидаемого, здоровая ≤ ожидаемого);
- [ ] фикстуры синтетические и **не сдвигают окна существующих демо**:
      максимальный `created_at` не позже `2026-11-09T02:59:30Z`
      (см. `FixtureGhArchiveClient`: сдвиг считается по самому позднему событию среди всех файлов).

### 3.2. `feat/c3-engagement` — C3 «Дисбаланс звёзды/активность» (Человек 2)

**План:** `engagement = (forks + issues + pulls + pushes) / max(stars, 1)`;
`s3 = clamp01((0.2 − engagement) / 0.2)`; `gate = min(1, stars / 20)`;
`score = s3 × gate`; пороги в `application.yaml`, `details` в explain;
фикстуры `star_stuffing` / `healthy_lib`.

**DoD ветки:**

- [x] `EngagementCheck` — Spring-бин, реальный C3 виден в `score.checks`;
- [x] `s3 ≥ 0.9` на `demo/star-stuffing`, `s3 ≤ 0.2` на `demo/healthy-lib`;
- [x] пороги в `app.scoring.checks.engagement.*` + валидация при старте;
- [x] переключатель `mock | real` (`app.scoring.mode`, точечно `app.scoring.checks.engagement.mode`);
- [x] `details`: `stars`, `activity`, `engagement`, `s3`, `gate`, пороги, `mocked=false`;
- [x] `confidence = 0` при `stars < min-stars-for-confidence` (C3 вне score);
- [x] unit- и интеграционные тесты (45 тестов суммарно), зелёные локально на JDK 25;
- [x] PR #2 открыт в `feature/core`;
- [ ] одно ревью и мерж PR #2 в `feature/core`;
- [ ] обновить README (вводная фраза «C1–C5 замоканы») и `docs/openapi.yaml`
      (описания «проверки замоканы») с учётом реального C3.

**Stretch (не входит в приёмку PoC):** C5 «Суточный профиль» (KL-дивергенция)
на синтетическом профиле, без включения в score. Принимается отдельным PR,
если останется время.

### 3.4. `feat/c1-burst` — C1 «Всплеск звёзд» (Человек 4)

**План:** `maxBurst10m` по `starsByMinute`, `baseline = median × 10`;
`ratio = burst / baseline`, `s1 = clamp01((ratio − 3) / 12)`;
`gate = min(1, maxBurst10m / 10)`, `score = s1 × gate`; warmup < 60 минут →
`confidence < 0.5`; `details`: окно, `ratio`. Фикстуры `burst_spike ≥ 0.9`,
`steady ≤ 0.2`.

**Дополнительно:** прогнать HTTP-режим на реальном часовом дампе, зафиксировать
размер и время загрузки.

**DoD ветки:**

- [ ] `BurstCheck` реализован реально и включён в score;
- [ ] тесты на фикстурах (`burst_spike`, `steady`) + границы формулы/конфига;
- [ ] HTTP-прогон на реальном репозитории: зафиксированы размер дампа и время ответа (цифры для демо);
- [ ] пороги и warmup в `application.yaml`, `details` в explain;
- [ ] фикстуры не сдвигают окна существующих демо;
- [ ] PR в `feature/core` с одним ревью.

### 3.5. `feat/c4-actor-overlap` — C4 «Пересечение акторов» (Человек 5)

**План:** глобальный индекс `actor → repos` по `WatchEvent` за окно
(top-500 репозиториев, bounded memory) — **согласовать с Человеком 1**;
`OverlapStats`: `JaccardMax`, `multiShare` (актор ставил звёзды ≥ 3 репозиториям);
`s4 = 0.5·clamp01((Jmax − 0.05) / 0.45) + 0.5·clamp01((multiShare − 0.1) / 0.4)`,
gate по `|A|`; фикстуры `farm ≥ 0.9`, `random_overlap ≤ 0.1`;
MinHash/LSH не делать.

**Дополнительно:** замер памяти/времени на 3-часовом дампе.

**DoD ветки:**

- [ ] `ActorOverlapCheck` + индекс; индекс не течёт по памяти при окне до 24 часов;
- [ ] тесты индекса и проверки; explain содержит `jaccardMax`, `multiShare`;
- [ ] если индекс не готов — `confidence < 0.5` и проверка вне score (не блокирует мерж остальных);
- [ ] цифры памяти/времени на 3-часовом дампе зафиксированы для демо;
- [ ] пороги в `application.yaml`, фикстуры `farm` / `random_overlap`;
- [ ] PR в `feature/core` с одним ревью.

### 3.6. `feat/top-1000-index` — предвычисленный индекс топ-1000 (Человек 1 + команда)

**Зачем:** запрос по случайному репозиторию сейчас скачивает и построчно парсит
все часовые дампы окна — это минуты на запрос. Индекс строится один раз в фоне:
один проход считает звёзды по репозиториям и выбирает топ-1000, второй —
агрегирует только их; запрос читает готовый snapshot и складывает нужное подокно.

**Что сделано (ветка создана поверх `origin/pr-2`, чтобы не конфликтовать с C3):**

- `app.index.*`: `enabled`, `top-n=1000`, `window-hours=6`, `build-on-startup`, `refresh-cron`;
- двухпроходная сборка (`RepoIndexBuilder`) и атомарная подмена snapshot (`RepoIndex`);
- почасовые агрегаты топ-репозиториев и композиция подокна `hours` (`RepoStatsComposer`);
- быстрый путь `RepoReportService` → `IndexRepoDataProvider`; fixture-режим индекс не использует;
- вне индекса — `404 REPO_NOT_INDEXED`; до прогрева — `503 INDEX_NOT_READY`;
- `GET /api/v1/index/repos?limit=1000` — rank, `owner/name`, `full_name`, звёзды за окно;
- обновлён OpenAPI; 60 тестов на JDK 25 (включая PR #2).

**DoD ветки:**

- [x] индекс строится фоново и подменяется атомарно; запрос по индексированному
      репозиторию не скачивает дампы;
- [x] топ-1000 выбирается по `WatchEvent` за окно с детерминированным тай-брейком;
- [x] `hours` в запросе не больше `app.index.window-hours`; иначе 400;
- [x] репозиторий вне индекса → `404 REPO_NOT_INDEXED` с подсказкой на эндпоинт топа;
- [x] до готовности индекса → `503 INDEX_NOT_READY`; в fixture-режиме индекс обходится;
- [x] `GET /api/v1/index/repos` отдаёт список доступных репозиториев и метаданные окна;
- [x] тесты: выбор топ-N, композиция окна, сборка snapshot без сети, 404/503, эндпоинт;
- [x] OpenAPI обновлён, README-раздел вынесен в `docs/top-1000-index.md`
      (README не трогаем, чтобы не конфликтовать с правками PR #2);
- [ ] PR в `main` после мержа PR #2; проверить, что конфликтов с C3 нет;
- [ ] после мержа — прогреть индекс на реальном окне и зафиксировать время/память.

**Ограничения:** первый прогрев — два прохода по дампам (минуты); репозиторий,
не попавший в топ по звёздам, недоступен через быстрый путь; акторы в индексе
считаются как сумма по часам (без дедупликации между часами) — для PoC-моков достаточно.

**Как проверить:** `mvn clean test`; после прогрева
`curl localhost:8080/api/v1/index/repos?limit=10`; запрос репозитория из топа;
запрос вне топа → `REPO_NOT_INDEXED`.

## 5. Ограничения GH Archive и как они учтены в DoD

GH Archive не содержит: даты создания аккаунта, истории за 90 дней, готового
индекса `actor → repos`, 7-дневного часового профиля. Поэтому:

- C2, C4, C5 работают на расширенном snapshot/фикстурах с **низким confidence**
  и не завышают score; отсутствие данных фиксируется в `DataAvailability`;
- проверка, у которой данных недостаточно, не должна влиять на итоговый score —
  это проверяется интеграционно (реальные данные → confidence < 0.5);
- демо «плохая/здоровая» фикстура — обязательный артефакт каждой ветки.

## 6. Как проверить статус ветки

```bash
# какие ветки есть на сервере и влиты ли они в feature/core
git fetch origin --prune
git branch -r --merged origin/feature/core

# открытые PR в feature/core (если установлен GitHub CLI)
gh pr list --base feature/core --json number,title,headRefName,reviewDecision

# тесты на JDK 25
mvn -B verify

# демо реальной проверки на фикстурах (пример C3)
mvn spring-boot:run -Dspring-boot.run.arguments="--app.archive.mode=fixture --app.scoring.checks.engagement.mode=real"

# индекс топ-1000 (HTTP-режим; пока не прогрет — 503)
curl "http://localhost:8080/api/v1/index/repos?limit=10"
```

Чек-лист ветки считается закрытым, только когда её PR смержен в `feature/core`
и после мержа `mvn verify` зелёный на голове `feature/core`.
