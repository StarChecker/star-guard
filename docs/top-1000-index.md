# Star Guard — индекс топ-1000 репозиториев

Документ объясняет, почему запрос по «случайному» репозиторию занимал минуты
и как сервис ускорен предвычисленным индексом. Ветка: `feat/top-1000-index`
(создана поверх `origin/pr-2`, чтобы не конфликтовать с C3).

## Почему было медленно

Старый путь `GET /api/v1/repos/{owner}/{name}` на **каждый новый репозиторий**:

1. скачивал все часовые gzip-дампы GH Archive за окно (по умолчанию 6 часов);
2. распаковывал и построчно JSON-парсил **каждое** событие;
3. только после разбора оставлял события нужного `repo.name`.

Кэш был ключом `(repo, hour)`, поэтому запрос по другому репозиторию ничего
не переиспользовал. Стоимость зависит от размера дампов, а не от популярности
репозитория: для случайного репозитория это десятки секунд–минуты и сотни МБ.

## Как устроен индекс

Индекс строится в фоне и отвечает на запросы без сети и JSON-парсинга:

```text
каждые N часов / на старте
        │
        ▼
RepoIndexBuilder
  один проход на час → HourDigest: счётчики, starsByMinute[60], акторы
                       всех репозиториев часа + StarIndex для C4
  дайджесты часов, оставшихся в окне, переиспользуются: при сдвиге окна
  разбирается только новый час (F3-2)
  топ-1000 по сумме звёзд дайджестов → агрегаты топа берутся из них же
        │
        ▼
RepoIndexSnapshot (immutable) ── атомарная подмена RepoIndex
        │
GET /api/v1/repos/... ──► IndexRepoDataProvider ──► RepoStatsComposer
        │                     (почасовые агрегаты → нужное подокно hours)
        └─ вне индекса → 404 REPO_NOT_INDEXED
           индекс строится → 503 INDEX_NOT_READY
```

- **Топ-1000** считается по числу `WatchEvent` за окно; тай-брейк — по имени.
- Для каждого часа хранятся: `EventCounts`, `starsByMinute[60]`, число
  уникальных акторов (сумма по часам — верхняя граница без дедупликации;
  для PoC-моков этого достаточно).
- Запрос с `hours < app.index.window-hours` складывает последние `hours`
  часовых агрегатов. Если `hours` больше окна индекса (но не больше 24), отчёт
  не падает с 400: сервер дочитывает недостающие дампы GH Archive напрямую —
  это медленный путь, для UI лучше фоновый скан. Окно индекса настраивается
  `app.index.window-hours` (1–24).
- `GET /api/v1/index/repos?limit=1000` отдаёт список: `rank`, `owner`, `name`,
  `full_name`, `stars` за окно, а также `window`, `built_at`, `hours_loaded`,
  `missing_hours`, `parse_errors`. Клиент заранее видит, какие репозитории
  можно запрашивать.
- Fixture-режим индекс не использует: тесты и демо остаются мгновенными.

## Конфигурация

```yaml
app:
  index:
    enabled: true
    top-n: 1000
    window-hours: 6
    build-on-startup: true
    refresh-cron: "0 10 * * * *"   # UTC, после задержки публикации GH Archive
```

- `enabled=false` — откат к прежнему прямому сканированию GH Archive;
- `build-on-startup=false` — индекс не прогревается на старте (удобно для тестов);
- до первой успешной сборки запросы получают `503 INDEX_NOT_READY`;
- при ошибке обновления остаётся предыдущий snapshot.

## Ошибки

| Ситуация | HTTP | `code` |
|----------|------|--------|
| Репозиторий вне топ-N | 404 | `REPO_NOT_INDEXED` |
| Индекс ещё не готов / отключён | 503 | `INDEX_NOT_READY` |
| `hours` больше окна индекса | 400 | `INVALID_REQUEST` |
| Ошибка загрузки/разбора дампа при сборке | — | час попадает в `missing_hours`, сборка продолжается |

## Проверка

```bash
mvn clean test                     # 60 тестов, офлайн
mvn spring-boot:run                # HTTP-режим, индекс прогревается в фоне
curl "http://localhost:8080/api/v1/index/repos?limit=10"
curl "http://localhost:8080/api/v1/repos/<из топа>?hours=6"
curl "http://localhost:8080/api/v1/repos/<не из топа>"   # 404 REPO_NOT_INDEXED
```

## Ограничения PoC

- первый прогрев — один проход по каждому часу окна (6 скачиваний), каждое следующее
  обновление — только новый час; при медленной сети до data.gharchive.org это всё равно
  минуты ([отчёт F3-2](f3-2-hourly-aggregates.md));
- дайджесты держат агрегаты всех репозиториев часов окна (сейчас ~7 МБ на 6 часов);
  уровни top-tier / long-tail и бюджет памяти — задачи F3-3 и F3-6;
- в индекс попадают только репозитории с наибольшим числом звёзд за окно;
- случайный репозиторий вне топа намеренно не сканируется — это и есть
  источник предсказуемой latency;
- для реального C2/C4 нужен расширенный snapshot (дата создания аккаунта,
  глобальный индекс actor→repos); сейчас это задачи отдельных веток.
